# v0.2.2 Release Notes

A fix release for the v0.2 series. The main fix is for the control plane's
**distribution**: a `KairosControlPlane` whose `spec.distribution` changed
after its Machines existed could skip the etcd leave of a departing k0s
member and leave a voting etcd member behind. The control plane now checks
`spec.distribution` against what its Machines run and holds instead of acting
on a mismatch. This release also stops the `KairosControlPlaneTemplate`
webhook from stamping `k0s` onto every ClusterClass control plane, stops k0s
post-bootstrap from holding up the rest of a node's boot, and builds the image
with Go 1.27.4.

There is no CRD schema change; only the description of `spec.distribution`
changes. Read [Upgrade notes](#upgrade-notes): check
that each control plane's `spec.distribution` matches its Machines before you
upgrade, because a control plane where they differ stops scaling right after
the upgrade.

## Highlights

- **The control-plane distribution follows its Machines** (#223).
  - **The problem:** `KairosControlPlane.spec.distribution` could change
    after control-plane Machines existed, through an operator edit, through
    Cluster API topology removing the field after a
    `KairosControlPlaneTemplate` dropped it, or through a switched template
    reference while it was empty. Nothing rolled out, so a k0s control plane
    relabelled `k3s` removed the etcd-leave hook from departing members
    without a `k0s etcd leave`, skipped orphan-member cleanup and admitted
    k3s joiners. The next scale-down, rollout or MachineHealthCheck
    remediation left a voting etcd member behind.
  - **The record:** the `KairosConfig` of each control-plane Machine records
    the distribution its node runs. The controller reads it on every
    reconcile. There is no new field or annotation.
  - **The hold:** when Machines exist and `spec.distribution` differs from
    what they run, or they disagree, or none of their `KairosConfig` objects
    can be read, the control plane creates and deletes no control-plane
    Machines, mints or extends no join tokens and removes no orphaned etcd
    members.
    Status, the kubeconfig, the etcd leave of a Machine an operator deleted,
    and deletion of the whole control plane keep working. `Ready` is False
    with reason `DistributionMismatch`, a Warning event names what each side
    says, and the control plane rechecks every 60 seconds. Set
    `spec.distribution` back to what the Machines run, or remove it, to
    release the hold. Changing the distribution of a running cluster is not
    supported: create a new Cluster.
  - **An empty `spec.distribution` is written back** from the Machines when
    they agree (event `DistributionRestored`), and from the
    `KairosConfigTemplate` only when there are no Machines
    (`DistributionInherited`). Once written, the controller owns the field,
    so a later topology apply without it does not remove it again.
  - **The etcd leave is decided by the hook.** Only k0s HA Machines are given
    the etcd-leave hook, so a departing Machine that carries it always runs
    the bounded leave. A `KairosConfig` that contradicts its Machine's hook
    no longer shortens the leave; it emits the Warning event
    `EtcdLeaveHookContradictsKairosConfig`.
  - **Admission:** changing `spec.distribution` between two non-empty values
    is admitted with a warning, not rejected, so a ClusterClass update cannot
    wedge every cluster on the class.

- **`KairosControlPlaneTemplate` no longer defaults `distribution` to `k0s`**
  (#222). A `KairosControlPlane` created from the template through a
  ClusterClass copied that value, and an explicit `k0s` overrode a `k3s`
  `KairosConfigTemplate`: the nodes got k0s cloud-config on a k3s image and
  nothing started. The template webhook now leaves the field unset, as the
  `KairosControlPlane` webhook already did.

## Fixed

- **A `kubeadm` `KairosConfigTemplate` is refused even with an explicit
  `spec.distribution`** (#223). Before, the refusal ran only when
  `spec.distribution` was empty, so a `KairosControlPlane` with an explicit
  `k0s` or `k3s` built control-plane Machines from a kubeadm worker spec.
  `Ready` is now False with reason `UnsupportedDistribution`, and no Machine
  is created or deleted.
- **k0s post-bootstrap no longer holds up the boot** (#155). The k0s
  post-bootstrap units are started with `systemctl --no-block`, so the
  cloud-config stage that starts them, and the users and SSH keys in the same
  cloud-config, no longer wait minutes for the join to finish. This completes
  the kubeadm and k3s fix from v0.2.1 (#149). On CAPK control planes, the
  update of the load-balancer certificate SANs is now ordered after
  post-bootstrap explicitly, and it no longer starts on the live installer or
  in recovery. The ordering is covered by a render test and was not run on a
  live CAPK k0s HA cluster.

## Security

- **Go 1.27.4.** The image is now built with Go 1.27.4. v0.2.1 was built with
  Go 1.26.10, which govulncheck reports as affected by GO-2026-6859
  (CVE-2026-97054) in `net/http`: an HTTP/1 server that limits request bodies
  with `MaxBytesReader` or `MaxBytesHandler` can crash if a handler reads the
  body while it writes the response header. The manager's webhook, metrics
  and health servers reach the affected `net/http` code, but no package
  linked into the manager uses `MaxBytesReader` or `MaxBytesHandler`, so we
  know of no way to trigger the crash in v0.2.1. Upgrade anyway.
- **Dependencies with advisories**, none of them reachable from the manager:
  - `golang.org/x/net` v0.62.0 (#209): GO-2026-6860 and GO-2026-6866, in its
    `html` package. govulncheck finds the package imported but not called.
  - `golang.org/x/crypto` v0.59.0 (#211): GO-2026-5932, the unmaintained
    `openpgp` package, which the manager does not link.
  - `go.opentelemetry.io/otel/trace` v1.47.0 (#214): GHSA-q7gw-24fr-5p69, an
    attribute-length limit that can be bypassed. The module comes in through
    Kubernetes libraries; the affected code is OpenTelemetry's
    auto-instrumentation tracer, and the manager sets up no tracing.
- **Release workflow** (#203, #213): the release job's checkout no longer
  keeps the token on disk, the unused QEMU setup step is gone, and a release
  that is missing one of its assets fails instead of publishing without it.
- **Base image:** the distroless runtime image is updated to a newer digest
  (#205).

## Upgrade notes

```bash
kubectl apply -f https://github.com/kairos-io/cluster-api-provider-kairos/releases/download/v0.2.2/kairos-capi-provider.yaml
```

Or, with `clusterctl`, upgrade both providers to v0.2.2.

- **Check each control plane's distribution before upgrading.** Compare each
  `KairosControlPlane`'s `spec.distribution` with the `spec.distribution` of
  its control-plane `KairosConfig` objects; the commands are in
  [UPGRADING.md](https://github.com/kairos-io/cluster-api-provider-kairos/blob/v0.2.2/docs/UPGRADING.md#check-the-control-plane-distribution-before-upgrading).
  A control plane where they differ is held right after the upgrade:
  `Ready` False with `DistributionMismatch`, and no scaling, rollout or
  remediation. To release it, set `spec.distribution` back to what the
  Machines run, or remove it. A consistent control plane sees no change, and
  an empty `spec.distribution` gets its Machines' value written back.
- **A `KairosControlPlane` with an explicit `k0s` or `k3s` that references a
  `kubeadm` `KairosConfigTemplate`** stops creating and deleting Machines.
- **`KairosControlPlaneTemplate` objects created by v0.2.1 or earlier** keep
  the `distribution: k0s` they were stored with. Set the field to the
  distribution your control planes run, or remove it; with this release,
  removing it is safe.
- **The k0s post-bootstrap change reaches only Machines created after the
  upgrade.** Bootstrap data is not re-rendered.

The full details are in
[UPGRADING.md: v0.2.1 to v0.2.2](https://github.com/kairos-io/cluster-api-provider-kairos/blob/v0.2.2/docs/UPGRADING.md#v021--v022).

## Not in this release

- Making a `KairosConfig`'s `spec.distribution` impossible to change once
  set. The control plane now relies on it, so this is planned as a separate
  change.

## Versions

- Unchanged from v0.2.1: Cluster API v1.13.4 (v1beta2 contract), management
  Kubernetes v1.32 to v1.36, workload Kubernetes v1.30 to v1.36, and Kairos
  v4.1.2.
- The image is built with Go 1.27.4. Building from source still needs Go
  1.26.4 or later.
