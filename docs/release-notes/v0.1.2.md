# v0.1.2 — Release Notes

A fix release. Every change came out of running the providers against real
infrastructure — KubeVirt, vSphere, Metal3, the Kairos fleet provider and a
bare-metal Beskar7 lab — for both k0s and k3s, single-node and
high-availability. No CRD or API change; no migration steps from v0.1.1.

Two themes run through it. The first is that a highly available control plane
on real hardware exposed a family of first-start races that a single-node or
virtualised lab never reaches: configuration that arrives seconds after the
distribution has already started, and joiners that raise etcd's quorum
requirement before they can serve. The second is that support for
infrastructure providers is no longer an allowlist.

## Highlights

- **Any CAPI-conformant infrastructure provider now works.** The infra-machine
  cloner and the control plane's node-IP lookup each hardcoded a list of
  provider kinds, so an unlisted provider was rejected outright with
  `unsupported infrastructure provider: <Kind>MachineTemplate`. Both now fall
  back to the contract: a `<Kind>MachineTemplate`'s `spec.template.spec` is the
  spec of the `<Kind>Machine` it produces, and `status.addresses` is mandatory
  on an InfraMachine. Group and version come from the template object itself.
  Adding a provider no longer requires a change here.

- **k3s HA no longer comes up as three unrelated single-node clusters.**
  `k3s.args` is delivered as a systemd drop-in, which on an instrumented run
  landed three seconds after `k3s.service` had already started. k3s picks its
  datastore on first start and never migrates, so `--cluster-init`, `--server`
  and `--token-file` were ignored for the life of the node. The failure was
  silent: the init node reported "etcd disabled", every joiner bootstrapped its
  own cluster with its own CA, and a 3-replica control plane reported Ready
  with no quorum anywhere. The flags that must be right on the first start are
  now also pinned in `config.yaml.d`, which k3s re-reads on every start and
  which the boot-stage `write_files` lands before that first start.

- **k0s controller arguments are pinned and applied even after a losing race.**
  The same drop-in timing problem cost k0s its flags on two of five measured
  boots, leaving a bare `k0s controller` with no worker role, so no kubelet, so
  no Node, so no `providerID` patch. Arguments now go in a `zz-capi-args.conf`
  drop-in that sorts last, and a post-bootstrap check compares the live argv
  against the effective `ExecStart` and restarts only when they differ. A join
  controller that came up without its token had initialised a cluster of its
  own; that state is discarded first, and only for a join node whose live argv
  provably lacks the token.

- **HA joiners are created one at a time.** The joinable gate only inspected the
  init machine, so once the init node was healthy every joiner was created in
  the same second. Each runs `etcd member add` on boot, so two adds against a
  one-member cluster raise the voter count to three while one member is
  serving: quorum is unmet, etcd stops serving, and the k0s join API — which
  needs the apiserver to validate a join token — hangs. Reproduced on four
  clusters across two providers, two OS bases and three images. The gate now
  requires every existing joiner to have finished joining, strictly for k0s and
  advisorily for k3s, which joins as a learner and cannot strand the cluster.
  The rollout surge path, which had no quorum check at all, gets the same gate.

- **A CRITICAL SSH authentication-bypass CVE is fixed.** `golang.org/x/crypto`
  is bumped past CVE-2026-56854, an authentication bypass in
  `golang.org/x/crypto/ssh` where source-address restrictions are not enforced.
  The SSH fallback worker authenticates with exactly that package, so this is
  not a transitive bystander. See Security below.

## Fixed

- The k0s controller-join token push made one attempt and, on failure, logged
  "will retry on next boot" from a oneshot unit that then exited zero with
  nothing to reboot the node. A single lost race stranded the cluster
  permanently, with the control plane holding every joiner for 45 minutes and
  counting. The push and the etcd-status report now retry.
- On CAPV — the default template for every non-KubeVirt provider — the k0s
  config carried neither `spec.api.address` nor `spec.storage.etcd.peerAddress`.
  On a dual-homed bare-metal node k0s then advertised its provisioning address,
  baked it into the controller-join token, and every joiner timed out against
  an unroutable endpoint. Both are now resolved before k0s starts, by routing:
  the source address the kernel would use to reach the control-plane endpoint,
  which is by definition one a joiner can reach. When no address can be found
  the resolver removes the settings and lets k0s auto-detect, rather than
  wedging the node.
- A `machineTemplate.infrastructureRef` that omits `namespace` is resolved in
  the `KairosControlPlane`'s own namespace, as the CAPI convention requires and
  as clusterctl-generated templates rely on. Previously the lookup failed with
  `an empty namespace may not be set when a resource name is provided`,
  surfacing only as `Ready=False` with no Machine and no infrastructure object.
- The CAPK HA samples pointed all three control-plane VMs at the same two named
  DataVolumes. Those PVCs are ReadWriteOnce, so only one VM could ever attach
  them and the samples could not work as written. Both now use
  `dataVolumeTemplates`, giving each cloned VM its own disks.

## Security

- `golang.org/x/crypto` v0.53.0 to v0.55.0, fixing **CVE-2026-56854
  (CRITICAL)**, an authentication bypass in `golang.org/x/crypto/ssh` caused by
  unenforced source-address restrictions.
- `golang.org/x/net` v0.55.0 to v0.57.0, fixing CVE-2026-46600 (HIGH), a denial
  of service in `dns/dnsmessage`.
- `golang.org/x/text` v0.38.0 to v0.41.0, fixing CVE-2026-56852 (HIGH), a
  denial of service on invalid UTF-8 input.

Scanning the release image with
`trivy image --severity CRITICAL,HIGH --ignore-unfixed --scanners vuln` now
reports zero findings for both the base layer and the manager binary.

**CI now runs that scan.** Nothing examined the published artifact before,
which is precisely how a CRITICAL reached a shipping image: the vulnerable
dependency merged months before the advisory existed, so no test, lint or build
job had any reason to complain. The new `Image scan` workflow builds the image
from the release `Dockerfile` and fails on any fixable CRITICAL or HIGH finding
in either the runtime base layer or the manager binary, on every push and pull
request, and again weekly on `main` so a newly disclosed CVE surfaces without
waiting for someone to push code. Unfixable findings are reported but do not
fail the job. See [docs/TESTING.md](../TESTING.md#image-scanning).

## Documentation

- The CAPK quickstart documents the **k0s image start gate**. A 3-node k0s
  control plane needs a Kairos image that stops k0s starting during the install
  boot. Kairos applies the cloud-config on every boot that carries it, so k0s
  starts inside the installer, joins, and is registered on the init node as a
  voting member — k0s has no learner join. The installer then reboots, leaving
  a configured-but-dead voter, and the control plane reports `Available=True`
  throughout while etcd stalls. The fix is image-side, so this provider cannot
  ship it; the quickstart carries the yip stage, the failure signature and how
  to verify the gate. k3s does not need it.
- [High-Availability control planes](../HIGH_AVAILABILITY.md#scale-up-joiners-are-created-one-at-a-time)
  explains serial joiner creation and what it means for scale-up time and for
  telling a slow rollout from a stalled one.
- [docs/API_REFERENCE.md](../API_REFERENCE.md) gains the
  `KairosControlPlane.spec.sshFallback` block. It has been implemented and
  referenced from the CAPV quickstart for some time but had no entry in the CRD
  reference at all, including its host-key verification settings. `role` is also
  corrected from required to optional, matching the CRD.
- Bug reports are directed at [kairos-io/kairos](https://github.com/kairos-io/kairos/issues).

## Upgrade notes

From v0.1.1 there are no migration steps and no CRD changes. A
`clusterctl upgrade` (or re-applying the release manifest) is enough.

Two things to know if you run HA control planes:

- Joiners are now created strictly one at a time. Scale-up takes longer by
  design, and a joiner that never comes up will hold the next one back with a
  visible reason on the `KairosControlPlane` rather than taking the cluster
  down.
- For k0s HA, check that your Kairos image carries the start gate described in
  the [CAPK quickstart](../QUICKSTART_CAPK.md). Without it a 3-node k0s control
  plane can strand itself during the install boot, and nothing in the provider
  can detect or repair that.
