# v0.2.3 Release Notes

A fix release for the v0.2 series. It hardens the k0s **etcd leave** that runs
when a control-plane Machine is deleted, and it makes the `KairosConfig`
fields the control plane relies on impossible to change once the object
exists. Three of the etcd-leave fixes close ways a departing k0s member's
leave could end early or be aimed at another member, either of which could
leave a voting etcd member behind. The fourth keeps `machineTemplate.metadata`
off the annotations the leave keeps its state in.

The `KairosConfig` CRD gains validation rules; no field is added or removed.
Read [Upgrade notes](#upgrade-notes) before you upgrade: tools that write
`KairosConfig` objects must send the stored `role`, `distribution` and
`hostname`, and a `machineTemplate.metadata` that sets an etcd-leave
annotation needs editing.

## Highlights

- **A `KairosConfig`'s role, distribution and control-plane hostname cannot
  change** (#231).
  - **The problem:** a `KairosConfig` records what its node runs and what it
    is called. Since v0.2.2 the control plane reads the distribution from it,
    and the k0s etcd leave of a Machine without a Node finds its member by the
    node's name. All three fields could be edited after creation, and a
    full-object update that omitted `role` or `distribution` got its default
    (`worker`, `k0s`). A control-plane `KairosConfig` could silently become a
    worker one, and a k3s one k0s.
  - **The rules:** four validation rules in the CRD reject, with `Forbidden`
    on the field, an update that:
    - changes `spec.role`, in either direction, or `spec.distribution`;
    - sets, changes or clears `spec.hostname` on a control-plane
      `KairosConfig` (`role: control-plane`);
    - removes `spec`.
  - **What still works:** creating a `KairosConfig` is not affected, so
    `MachineSet` scale-ups, `clusterctl move` and restores from a backup keep
    working. Every other update works as before, and no stored object becomes
    invalid. `KairosConfigTemplate` is not restricted. The rules live in the
    CRD, so they hold without the webhook. To change one of these fields,
    replace the Machine.
  - v0.2.2 listed the `spec.distribution` rule under "Not in this release".

- **The k0s etcd leave of a Machine without a Node uses a recorded node
  name** (#225).
  - **The problem:** for a k0s control-plane Machine without a Node, the leave
    took the etcd member's name from the Machine's `KairosConfig`
    `spec.hostname`, or the Machine name when the `KairosConfig` was gone, and
    worked it out again on every pass. Editing, deleting or recreating the
    `KairosConfig` changed the name the leave looked for; a foreground delete
    of the Machine can remove the `KairosConfig` before the leave runs. The
    leave then found no member, or mistook another Machine's for it, and the
    hook was removed without a leave.
  - **The record:** each control-plane Machine the controller creates now
    carries the annotation `controlplane.cluster.x-k8s.io/rendered-node-name`,
    the name its node is rendered with, set when the Machine is created. The
    leave looks the member up by the Node name, then the record, then, for a
    Machine without a record, the `KairosConfig`. An existing control-plane
    Machine that is not being deleted gets the annotation on the first
    reconcile after the upgrade, if its node name can be determined and is a
    lowercase DNS-1123 label.
  - **Re-checked on every pass:** once the leave of a Machine without a Node
    is requested, its node name is checked again on every pass before the
    controller touches the workload cluster. If the name has since become one
    that is not a lowercase DNS-1123 label, or that another control-plane
    Machine of the Cluster may go by, the leave is held with the Warning event
    `EtcdLeaveNodeNameUnusable` until the name is restored or the usual time
    limit passes, and is never handed to k0s. A `KairosConfig` that renders
    another name than the record emits the Warning event
    `EtcdLeaveNodeNameContradictsKairosConfig`, and the leave proceeds with the
    recorded name. Both events are recorded on the `KairosControlPlane`.

## Fixed

- **A k0s member's absence from the etcd-status Secret no longer ends its
  etcd leave** (#227). Before, once the leave of a control-plane Machine with
  a Node was requested, it ended, and its hook was removed, as soon as the
  node had no entry in `<cluster>-etcd-status`. Nodes write that entry once,
  at boot, and nothing removes it, so a missing entry never meant the member
  had left. It was missing when, for example, the node never reported,
  reported under a name other than its Node name, or the Secret was deleted
  or recreated, and the member could still be voting. The leave now ends only
  when the node acks it, when k0s reports the member not joined after the
  leave is handed to it, or with `EtcdMemberLeaveTimedOut`.
- **The etcd-leave checks see every control-plane Machine of the Cluster**
  (#228). The checks that keep a leave off a member that may belong to
  another Machine, by peer address and by node name, looked only at the
  Machines this `KairosControlPlane` owns. Control-plane Machines of the same
  Cluster with another owner, or none, now count too, and a leave whose member
  may be theirs is released with `EtcdMemberLeaveTimedOut` without being run.
  When the checks cannot run, because listing the Machines fails or a node
  name cannot be read from a `KairosConfig`, the leave is released after the
  usual ~15 minutes without being handed to k0s. Before, an unreadable node
  name held the leave of a Machine without a Node for as long as the error
  lasted.
- **`machineTemplate.metadata` no longer copies the etcd-leave annotations**
  (#226). The etcd-leave pre-terminate hook and the four annotations the leave
  keeps its state in (`etcd-leave-requested-at`,
  `etcd-leave-unreachable-since`, `etcd-member-leave-requested-at` and
  `etcd-member-leave-member-id`) are now reserved, as `rendered-node-name` is.
  Before, a template that set one of them put it on every control-plane
  Machine. A template hook made k3s and single-node Machines wait on a k0s
  etcd leave when deleted, and could be put back after the controller removed
  it. The other four made a later leave start as if it had already been
  requested. The controller now removes those four from Machines that are not
  being deleted. It keeps an etcd-leave hook it finds on a Machine, because
  the hook decides whether the Machine gets an etcd leave; see
  [Upgrade notes](#upgrade-notes) for removing one a template put there.
- **Machines being deleted no longer receive `machineTemplate.metadata`**
  (#226), so another controller's pre-terminate or pre-drain hook in the
  template is no longer put back after that controller removes it.

## Upgrade notes

```bash
kubectl apply -f https://github.com/kairos-io/cluster-api-provider-kairos/releases/download/v0.2.3/kairos-capi-provider.yaml
```

Or, with `clusterctl`, upgrade both providers to v0.2.3. The `KairosConfig`
validation rules ship in the CRD, so they arrive with either of these; a new
controller image on its own does not carry them.

- **Check `KairosConfig` role, distribution and hostname before upgrading.**
  Revert any edit to these fields that you mean to revert; after the upgrade,
  only replacing the Machine changes them. Tools that write `KairosConfig`
  objects directly, such as GitOps pipelines or scripts, must send the stored
  `role`, `distribution` and, for control-plane configs, `hostname`, or every
  sync is rejected. The command that lists the stored values is in
  [UPGRADING.md](https://github.com/kairos-io/cluster-api-provider-kairos/blob/v0.2.3/docs/UPGRADING.md#check-kairosconfig-role-distribution-and-hostname-before-upgrading).
- **Remove the etcd-leave annotations from `machineTemplate.metadata`**
  before you upgrade, if a template sets any of them. If a template put the
  etcd-leave hook on k3s or single-node control-plane Machines, remove it
  from each of them:

  ```bash
  kubectl annotate machine -n <namespace> <machine-name> pre-terminate.delete.hook.machine.cluster.x-k8s.io/kairos-etcd-leave-
  ```

  On a k3s control plane, the `KairosControlPlane` holds every membership
  change with `DistributionMismatch` until you do. You do not need to delete
  the Machines.
- **Deleting a k0s control-plane Machine can take longer.** When its node
  never reported, or its etcd-status entry is missing for another reason,
  the deletion now waits for the node's ack, for k0s, or for
  `EtcdMemberLeaveTimedOut` (at the latest after ~15 minutes) instead of
  finishing at once. Rollouts and the orphan-member cleanup wait with it.
- **Existing control-plane Machines get the `rendered-node-name`
  annotation** on the first reconcile after the upgrade, one patch per
  Machine, unless the Machine is being deleted or its node name cannot be
  determined or is not a lowercase DNS-1123 label. Do not set the
  key in `machineTemplate.metadata`: it is not copied. A downgrade ignores the
  annotation.

The full details are in
[UPGRADING.md: v0.2.2 to v0.2.3](https://github.com/kairos-io/cluster-api-provider-kairos/blob/v0.2.3/docs/UPGRADING.md#v022--v023).

## Known gap

A control-plane `KairosConfig` can still be deleted and recreated. Recreating
it with another hostname after its Machine is created, but before the node has
bootstrapped, makes the recorded name differ from the name the node takes; so
does an edit made before the upgrade. That Machine's leave then finds no etcd
member under the recorded name and is released without a leave. Do not
recreate a control-plane `KairosConfig` with another hostname: replace the
Machine. See
[HIGH_AVAILABILITY.md](https://github.com/kairos-io/cluster-api-provider-kairos/blob/v0.2.3/docs/HIGH_AVAILABILITY.md#day-2-etcd-health-and-quorum-safe-replacement).
