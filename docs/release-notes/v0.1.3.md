# v0.1.3 — Release Notes

A fix and supply-chain release. One real bootstrap bug, found on bare metal,
and the migration to the kairos-io org's scanning and dependency tooling. No
CRD or API change, and no migration steps from v0.1.2.

## Highlights

- **Bootstrap data is no longer rendered before the control-plane endpoint
  exists.** This is the fix to take if you run highly available control planes.
  A node installs from the first bootstrap Secret it is handed, so a Secret
  rendered too early is not something a later regeneration can repair.

  On a 3-replica k0s control plane using `spec.ha.vip`, the bootstrap Secret was
  written at 10:01:20 and Cluster API only wrote
  `Cluster.spec.controlPlaneEndpoint` at 10:01:43. The endpoint is baked into
  the render — it gates the `/etc/k0s/k0s.yaml` `api.sans` block and the
  `push_kubeconfig` rewrite — so the node installed with no `/etc/k0s/k0s.yaml`,
  k0s came up with SANs that did not include the VIP, and the node pushed
  `server: https://localhost:6443` into the cluster kubeconfig. Cluster API
  could not reach the workload cluster, the Machine never got a `NodeRef`, and
  the control plane logged "Holding back join machine until init machine is
  joinable" indefinitely. A correct render arrived three minutes later and
  changed nothing, because the node had already installed.

  `Reconcile` now waits for `Cluster.status.initialization.infrastructureProvisioned`
  before rendering, exactly as CABPK does. A control-plane role additionally
  waits for a usable `Cluster.spec.controlPlaneEndpoint`, so an infrastructure
  provider that reports provisioned without publishing an endpoint cannot
  reintroduce the broken render. Workers are not gated on the endpoint, since
  their render already tolerates its absence. While waiting, `Ready`,
  `BootstrapReady` and `DataSecretAvailable` carry
  `WaitingForClusterInfrastructure` at severity `Info`.

  A `Cluster` watch re-reconciles waiting configs the moment the cluster is
  provisioned, rather than leaving them to be picked up by an unrelated event.

- **Scanning and dependency updates now follow the kairos-io org practice.**
  Trivy is replaced by Google's reusable OSV-Scanner workflow; Dependabot by
  Renovate. See Changed below for what that does and does not cover.

## Fixed

- `KairosConfig` waits for cluster infrastructure before rendering (see
  Highlights).

## Security

- `golang.org/x/crypto` v0.55.0 to v0.56.0, clearing **GO-2026-6354** and
  **GO-2026-6355**; `golang.org/x/mod` v0.38.0 to v0.40.0, clearing
  **GO-2026-6179** and **GO-2026-6180**.

  Worth noting how these were found. v0.1.2 moved `x/crypto` to v0.55.0
  specifically to clear a CRITICAL SSH authentication bypass; two further
  advisories were published against that version within three days. OSV-Scanner
  surfaced them on the very pull request that introduced it. That is the case
  the weekly scheduled scan exists for — an advisory lands against code that
  has not changed, so nothing code-triggered would ever flag it.

- Both base images in the `Dockerfile` are pinned by digest, so a repointed
  upstream tag cannot change what ships. The pins are multi-arch **index**
  digests, verified by building `linux/amd64,linux/arm64` the way the release
  workflow does; pinning a per-platform manifest instead would break the arm64
  half of the release.

## Changed

- **OSV-Scanner replaces Trivy.** It runs on pull requests, on pushes to `main`,
  and weekly, and reports into Security > Code scanning rather than only into a
  job log.

  One scope change worth stating plainly: Trivy scanned the built image
  including its base layer, while OSV-Scanner reads declared dependencies. Go
  module vulnerabilities — the class that has actually affected this project —
  remain covered. Base-image CVEs are now addressed by the digest bumps Renovate
  proposes, not by a scanner.

  `osv-scanner.toml` carries exactly one ignore, `GO-2026-5932`. It is not a CVE
  and has no fixed version in any release: it records that
  `golang.org/x/crypto/openpgp` is unmaintained and unsafe by design, and it
  applies only to code importing those packages. This module does not — the file
  records the command to re-verify that.

- **Renovate replaces Dependabot**, configured in `renovate.json`, and Dependabot
  security updates are disabled at the repository level. Its commits carry a
  `Signed-off-by` trailer so they satisfy the DCO check. Two groups are held for
  explicit approval on the dependency dashboard rather than opened
  automatically, because each is a single coordinated decision: the Go toolchain
  (the `go` directive, the CI `go-version` pins and the builder image move
  together), and the Cluster API plus Kubernetes library set
  (`sigs.k8s.io/cluster-api vN` is built against one `k8s.io/*` minor and one
  controller-runtime minor; mixing them breaks the v1beta2 contract).

- The e2e harness pins the CDI manifests to **v1.66.1** rather than fetching
  `releases/latest/download`. That was the last input to the e2e management
  cluster that could change with no commit here. The pin is behaviour-preserving
  — v1.66.1 is what `latest` resolved to — and unit tests now guard every
  manifest URL in `internal/kubevirtenv` against a silent return to a floating
  tag, which `go vet` alone cannot catch.

## Upgrade notes

From v0.1.2 there are no migration steps and no CRD changes. A
`clusterctl upgrade`, or re-applying the release manifest, is enough.

One behaviour change to expect: a `KairosConfig` now sits at
`WaitingForClusterInfrastructure` until its `Cluster` reports
`infrastructureProvisioned`, and a control-plane config also waits for
`spec.controlPlaneEndpoint`. During normal provisioning this clears on its own
within seconds. If it does not, the infrastructure provider has not reported
the cluster provisioned, or has reported it without publishing an endpoint —
look at the InfraCluster.
