# v0.2.1 — Release Notes

A fix release for the v0.2 series. The main fix is for **k0s control planes
with high availability**: under a specific failure sequence, a joining k0s
controller could start a new, empty cluster with the same CA instead of
joining. The VIP then followed it, and the original cluster was lost while
every condition stayed True. This release closes that from both sides, on the
joining node and in the `KairosControlPlane`. It also hardens how the manager
holds Secrets and which clusters it connects to, and gates releases on a
vulnerability scan.

There is no CRD schema change. Read [Upgrade notes](#upgrade-notes): new
control-plane Machine names, a validated control-plane hostname, and a
workload identity pin that we recommend pre-seeding on HA clusters.

## Highlights

- **A k0s control plane can no longer be silently replaced by a new
  cluster** (#193, #194, #195, #196).
  - **The trigger:** a control-plane Machine that had joined etcd but never
    got a Node was deleted without leaving etcd, which orphaned its member.
    The next joiner failed half-way through its join. When it restarted, k0s
    started a fresh cluster instead of retrying.
  - **On the node (#196):** a joining k0s controller clears a half-written
    etcd database before it starts, so a restart joins again. If it finds it
    is the only etcd member, it stops k0s and never registers, so the Machine
    is replaced instead of serving a separate cluster.
  - **In the control plane (#193):** the `KairosControlPlane` pins the
    workload cluster's identity (its `kube-system` namespace UID). Before
    every membership change, it checks that it is still talking to the same
    cluster. If the identity changes, it freezes: no control-plane Machine is
    created or deleted, `Ready`, `Available` and `EtcdHealthy` go False with
    reason `WorkloadClusterIdentityChanged`, and only an operator can clear
    it.
  - **Leaving etcd (#194):** a control-plane Machine without a Node now
    leaves etcd before it is released. A leave that cannot reach the cluster
    is bounded at about 15 minutes. The control plane also removes etcd
    members that no Machine accounts for, one at a time and only when quorum
    allows, as the upstream kubeadm control plane does.
  - **Names (#195):** control-plane Machine names are random and never
    reused.

  These were validated live on vSphere with 3× k0s and a kube-vip VIP. The
  test deleted a joiner while its etcd member existed and before it had a
  Node. The control plane removed the member and etcd returned to the live
  members. A fresh join under the same conditions succeeded, and the
  original cluster survived every step.

- **The manager no longer keeps Secret bodies in memory** (#199). Secrets are
  read live, and the manager watches Secrets by metadata only. Before, it held
  every Secret in its scope, including every workload cluster's
  `<cluster>-kubeconfig`.

- **The kubeadm worker path connects only where it needs to** (#200). It no
  longer keeps a connection open to every KubeadmControlPlane or Kamaji
  cluster. It connects on demand, when one of its own kubeadm workers joins
  or refreshes its token, using the kubeconfig that passed the trust check.

## Fixed

- **Control-plane Machine without a Node** (#194): deleting one now runs a
  real etcd leave, keyed on the Machine's hostname. Before, the hook was
  removed at once and the member was left behind.
- **Leave bound** (#194): if no workload API server answers before the first
  leave request, the hook is held for about 15 minutes and then released with
  a Warning. Before, it could wait indefinitely.
- **Name reuse** (#195): deleting the newest control-plane Machine used to
  hand its name to the replacement.
- **Post-bootstrap no longer blocks boot** on kubeadm and k3s nodes (#149).
  The rest of the boot stage, such as users and SSH keys, no longer waits for
  the join to finish. The providerID drop-ins are now written atomically.

## Security

- **Secrets** (#199): see Highlights. The manager reads Secrets live, and the
  metadata it caches has `managedFields` and the last-applied annotation
  removed. RBAC is unchanged.
- **Workload connections** (#200): see Highlights. Every request through the
  on-demand client is bounded by a 10s timeout.
- **Release gate** (#197): a release now runs a whole-tree vulnerability scan
  (osv-scanner v2.7.0) on the tagged tree and stops if it finds an open
  advisory or cannot complete the scan. The release workflow's write
  permissions are limited to the release job.
- **Go 1.26.10.** The image is now built with Go 1.26.10, which
  fixes GO-2026-6809 (CVE-2026-111943) in `crypto/x509`: certificate
  verification trusted a set of compromised intermediate certificates. The
  controllers verify TLS certificates on every connection to a management or
  workload API server, so this one applies.
- **Pull request scans** (#198) compare a pull request with its base branch,
  so an advisory already on `main` no longer marks unrelated pull requests
  red. The whole-tree scan runs on `main`, weekly, and at release.

## Upgrade notes

```bash
kubectl apply -f https://github.com/kairos-io/cluster-api-provider-kairos/releases/download/v0.2.1/kairos-capi-provider.yaml
```

Or, with `clusterctl`, upgrade both providers to v0.2.1.

- **Pre-seed the workload identity pin on existing HA clusters.**
  - Existing HA control planes are pinned on the first reconcile after the
    upgrade, to whatever cluster answers then.
  - To be sure that is the right one, verify the `kube-system` UID through
    every control-plane member, then set the pin annotation by hand before
    upgrading. A pre-set pin is never replaced.
  - See
    [Before upgrading an existing HA cluster](../HIGH_AVAILABILITY.md#before-upgrading-an-existing-ha-cluster).
- **While a control plane is frozen**, anything that waits on the Cluster
  being `Ready` or `Available` (GitOps health checks, the fleet provider)
  holds. That is intended. Worker joins continue. The runbook is in
  [HIGH_AVAILABILITY.md](../HIGH_AVAILABILITY.md#runbook-workloadclusteridentitychanged).
- **New control-plane Machines get random names**, `<kcp-name>-<5
  characters>`. Existing Machines keep their names until they are replaced.
  Find control-plane Machines by label, not by name.
- **A new or changed control-plane `spec.hostname`** must be a lowercase
  DNS-1123 label without `{{`. Existing objects are unaffected until the field
  changes, and worker configs are not checked.
- **The k0s join guard reaches only control-plane members created after the
  upgrade.** Bootstrap data is not re-rendered.

The full details are in
[UPGRADING.md — v0.2.0 → v0.2.1](../UPGRADING.md#v020--v021).

## Not in this release

- Applying `spec.dnsServers` before runcmd. It changes the field's
  semantics, so it will be decided separately.
- Non-blocking post-bootstrap on k0s nodes. It is waiting for a live k0s HA
  run.

## Versions

- Unchanged from v0.2.0: Cluster API v1.13.4 (v1beta2 contract), management
  and workload Kubernetes v1.30 to v1.36, and Kairos v4.1.2.
- The image is built with Go 1.26.10.
