# v0.1.4 — Release Notes

A fix release for the v0.1 series. It contains ten control-plane and
bootstrap fixes found since v0.1.3, and the Go security updates published
since. It is cut from `main` immediately before the kubeadm worker
distribution merged, and contains none of that work. kubeadm workers arrive
in v0.2.0.

There is no CRD schema change. One change can reject an update that v0.1.3
accepted: a reference to another namespace. Check for those before
upgrading; see [Upgrade notes](#upgrade-notes).

## Highlights

- **A control-plane rollout no longer deletes a member before its
  replacement has joined** (#117). A `spec.version` change fell through from
  the rollout step to the plain scale-down path, and that path deletes an
  outdated Machine at once.
  - **HA control planes:** this removed an old etcd member while its
    replacement was still booting. A bad new image then left two healthy
    members and a dead one.
  - **Single-node control planes:** the replacement is created as a new
    standalone cluster rather than a member of the existing one, and the next
    pass deleted the original. The only control plane, and everything the
    cluster held, was replaced by an empty cluster.

  What happens now:
  - **Single-node:** the control plane is no longer rolled out by
    replacement. The Machine is left alone, and the new `MachinesUpToDate`
    condition reports `False` with reason `SingleNodeRolloutUnsupported`
    (severity `Warning`).
  - **HA:** an outdated Machine is removed only after every up-to-date
    Machine has joined, still behind the etcd quorum guard. Only one
    membership change is in flight at a time.

- **A CAPK cluster installed with `clusterctl` can now become reachable**
  (#118).
  - The control-plane controller fills the API load balancer's endpoints from
    each control-plane VirtualMachineInstance, but only the bootstrap
    provider's role allowed reading VMIs.
  - The flat manifest merges both roles, so it worked there. Under
    `clusterctl`, every read was forbidden, the load balancer never got a
    backend, and the cluster never became reachable.
  - The forbidden read was logged only at V(4), as though the VMI simply had
    no IP yet. It is now logged at the default level.

- **References to another namespace are refused** (#119). A `KairosConfig`
  could copy another namespace's Secret into bootstrap data its author can
  read. See [Security](#security).

- **`Cluster.spec.paused` is respected, and `clusterctl move` carries the
  templates it needs** (#109, #110, #120). Together these make
  `clusterctl move` work for Kairos clusters. Before, the controllers kept
  reconciling through the move, and the moved cluster arrived naming
  templates that had stayed behind on the source.

## Fixed

- **Pause** (#109). Neither reconciler checked whether the Cluster was
  paused, so a paused control plane still created and deleted Machines, and a
  paused bootstrap config still rendered userdata. Both now stop while
  `Cluster.spec.paused` or the `cluster.x-k8s.io/paused` annotation is set.
- **Deletion while paused** (#120). Deleting a `KairosControlPlane` whose
  Cluster was paused went straight into teardown. That marks every
  control-plane Machine for deletion and strips their etcd-leave hooks, and
  neither can be undone. Deletion now waits until the Cluster is unpaused. A
  Cluster that has already been deleted holds nothing back.
- **`clusterctl move`** (#110).
  - The referenced infrastructure machine template and `KairosConfigTemplate`
    now carry an owner reference to the Cluster, so `clusterctl move` carries
    them.
  - It is deliberately not a controller reference, because templates are
    shared by design.
- **`machineTemplate.nodeDrainTimeout`** (#112, #115).
  - It was accepted and ignored, so a drain blocked by an unevictable pod
    held the Machine forever. It is now copied to the Machine's
    `spec.deletion.nodeDrainTimeoutSeconds`, including on Machines that
    already exist.
  - A duration too large for int32 seconds is capped instead of wrapping
    round to "no deadline".
  - kairos-io/kairos#4895, kairos-io/kairos#4922.
- **`machineTemplate.metadata`** (#114).
  - Labels and annotations reached only the infrastructure machine, never
    the `Machine`. Cluster API copies labels to the Node only from the
    `Machine`, so a node-role label set on the control plane never reached
    the node it was written for.
  - Both objects now take their metadata from one place.
  - Existing Machines are updated too. The merge is additive: removing a key
    from the template leaves it on Machines that already carry it.
  - kairos-io/kairos#4896.
- **`caCertHashes` and `caCertSecretRef`** (#116).
  - These `KairosConfig` fields were documented as securing the node join,
    but nothing reads them.
  - Setting either now returns an admission warning, and the API reference
    says what to use instead.
  - They are not removed: that would be a breaking change to a served API
    version, and belongs in v1beta3.
  - kairos-io/kairos#4937.

## Security

- **References to another namespace are refused** (#119).
  - **Secret references on `KairosConfig`:** `userPasswordSecretRef`,
    `workerTokenSecretRef`, `k3sTokenSecretRef` and
    `controlPlaneJoinTokenSecretRef` accepted any namespace. The controller
    reads Secrets cluster-wide and copies what they point at into the
    bootstrap Secret it writes beside the `KairosConfig`. Anyone allowed to
    create a `KairosConfig` could therefore copy another namespace's Secret
    into data they can read.
  - **`KairosControlPlane.spec.machineTemplate.infrastructureRef`:** it also
    accepted any namespace. The controller cloned another namespace's
    template and marked the Cluster as its owner. Kubernetes treats an owner
    in another namespace as absent, so the garbage collector was free to
    delete that template.
  - A reference must now name the object's own namespace, or leave the
    namespace empty. Both validating webhooks reject anything else, and the
    controllers refuse it too, because a webhook is not always in the request
    path.
  - `tokenSecretRef` is unchanged, because the controller already ignores its
    namespace.
- **The image is built with Go 1.26.9**, up from 1.26.8. That clears these
  standard-library advisories:
  - `net/http` and HTTP/2: GO-2026-6603, GO-2026-6605, GO-2026-6609,
    GO-2026-6610, GO-2026-6611, GO-2026-6612, GO-2026-6613 and GO-2026-6617;
  - `crypto/tls`: GO-2026-6607;
  - `net/textproto` and `mime/multipart`: GO-2026-6608;
  - `html/template`: GO-2026-6599 and GO-2026-6600;
  - `os`, Windows only: GO-2026-6604.

  The provider runs HTTP servers (webhooks, metrics, health) and talks HTTP/2
  to the API server, so most of these apply to it.
- **`golang.org/x/net` v0.58.0 to v0.60.0** (#143). This clears GO-2026-6603,
  GO-2026-6610, GO-2026-6611, GO-2026-6612 and GO-2026-6617, the HTTP/2
  denial-of-service issues in `x/net`'s copy of HTTP/2. The binary also
  links the standard library's own copy, and the Go 1.26.9 builder above
  fixes that one. The bump carries `x/crypto` to v0.57.0, along with `x/sys`,
  `x/term`, `x/text`, `x/mod` and `x/sync`.
- **CVE-2026-41178 (`go.opentelemetry.io/otel`) does not affect this
  release.** No OpenTelemetry package is part of the build; that dependency
  arrived on `main` with the kubeadm work.

## Changed

## Documentation

- **The `clusterctl` provider URLs in the install guide were in a form
  `clusterctl` does not parse** (#111).
  - The documented pin example failed outright.
  - The registration URLs in the `releases/latest/download/...` form work
    only through `clusterctl`'s fast path. They fail once it falls back to the
    GitHub API, which happens on a rate-limited or proxied network or under
    `GOPROXY=off`.
  - If you copied those URLs, see the [Upgrade notes](#upgrade-notes).
- **The sample manifests were rejected by the API server**, so the CAPD
  quickstart could not be followed as written (#111).
  - Three DockerMachineTemplates had an empty `spec.template.spec`.
  - The MachineDeployments used the v1beta1 reference shape.
  - Two MachineDeployments lacked `clusterName`.
  - Sixteen of the 22 samples now validate with
    `kubectl apply --dry-run=server` as shipped. The other six (the CAPV
    cluster samples and the CAPM3 HA samples) validate once their
    placeholders are filled in.
- [docs/API_REFERENCE.md](../API_REFERENCE.md) covers the drain timeout, the
  machine metadata, the `caCertHashes`/`caCertSecretRef` warning and the
  `MachinesUpToDate` condition.

## Upgrade notes

### 1. Check for references to another namespace

Do this before upgrading. After the upgrade, an update to an object that
names another namespace is rejected. A `KairosConfig` stamped from a
`KairosConfigTemplate` that does so is rejected when Cluster API creates it,
which stalls that MachineDeployment's scale-up. Both commands print nothing
when there is nothing to fix:

```bash
kubectl get kairosconfigs,kairosconfigtemplates -A -o json | jq -r '
  .items[] | . as $o
  | ($o.spec.template.spec // $o.spec) as $s
  | ("userPasswordSecretRef", "workerTokenSecretRef", "k3sTokenSecretRef", "controlPlaneJoinTokenSecretRef") as $f
  | ($s[$f].namespace // "") as $ns
  | select($ns != "" and $ns != $o.metadata.namespace)
  | "\($o.kind) \($o.metadata.namespace)/\($o.metadata.name): \($f) -> \($ns)"'

kubectl get kairoscontrolplanes -A -o json | jq -r '
  .items[]
  | (.spec.machineTemplate.infrastructureRef.namespace // "") as $ns
  | select($ns != "" and $ns != .metadata.namespace)
  | "KairosControlPlane \(.metadata.namespace)/\(.metadata.name): machineTemplate.infrastructureRef -> \($ns)"'
```

For each line printed, copy the Secret or template into the object's own
namespace, and point the reference at that copy, or clear its `namespace`.

### 2. Fix `clusterctl.yaml` if it uses `releases/latest/download/`

A provider `url` must have the form
`https://github.com/kairos-io/cluster-api-provider-kairos/releases/latest/<file>`
(or `releases/<tag>/<file>`), with no `download/` segment. See
[INSTALL.md](../INSTALL.md).

### 3. Upgrade

`clusterctl upgrade`, or re-applying the flat manifest, is enough:

```bash
kubectl apply -f https://github.com/kairos-io/cluster-api-provider-kairos/releases/download/v0.1.4/kairos-capi-provider.yaml
```

The CRDs change only in field descriptions. Under `clusterctl`, the
control-plane provider's role gains `get` on
`kubevirt.io/virtualmachineinstances`.

### Behaviour changes to expect

- **Single-node control planes:** a `spec.version` change no longer replaces
  the Machine. `MachinesUpToDate` reports `SingleNodeRolloutUnsupported`
  instead.
- **HA rollouts** proceed one membership change at a time, and wait for each
  replacement to join.
- **`machineTemplate.nodeDrainTimeout`**, if you set it, now bounds the drain.
- **`machineTemplate.metadata`** is now applied to existing control-plane
  Machines, and its labels in Cluster API's synced domains reach the Nodes.
- **Pause:** a paused Cluster now stops reconciliation, and holds a
  `KairosControlPlane` deletion until it is unpaused.
- **`caCertHashes` or `caCertSecretRef`:** setting either produces an
  admission warning.
