# v0.2.0 — Release Notes

The first release of the v0.2 series. It adds **kubeadm workers**: Kairos
worker nodes that join a control plane managed outside this provider, such as
a Kamaji `KamajiControlPlane` or a Cluster API `KubeadmControlPlane`. It also
hardens how the provider handles workload-cluster kubeconfigs and how nodes
talk to the management cluster, and carries every fix from v0.1.5.

**Upgrade promptly.** The kubeconfig handling changes are a security
hardening; see [Security](#security). There is no CRD schema change, but some
behaviour changes; read [Upgrade notes](#upgrade-notes) before upgrading.

## Highlights

- **kubeadm workers** (#141, #148, #191). Set `spec.distribution: kubeadm` on
  a `KairosConfig` or `KairosConfigTemplate` to bootstrap a Kairos worker that
  joins a kubeadm-based control plane with `kubeadm join`.
  - **Supported control planes:** `KamajiControlPlane` and `KubeadmControlPlane`
    out of the box. Other kinds can be allowed with
    `--kubeadm-extra-controlplane-kinds`.
  - **Validated live:** with Kamaji, in three configurations, and with an
    upstream `KubeadmControlPlane` on KubeVirt (join, trust checks and DNS).
  - **Token handling:** the provider mints a bootstrap token per worker,
    checks that the control plane's kubeconfig and CA belong to the cluster
    before it does, and keeps that one token alive until the node joins, so a
    slow install or a reboot before `kubeadm join` no longer fails (#191).
  - **Customisation:** `spec.kubeadm.joinConfiguration` takes the same fields
    as Cluster API's kubeadm `JoinConfiguration`. Kubelet patches go in a
    patches directory under `/etc/kubernetes/` (#148).
  - **Not in scope:** a kubeadm control plane run by this provider,
    `MachinePool` workers, and CNI installation.

  See [Kubeadm Workers](../KUBEADM_WORKERS.md) for prerequisites, the scope
  table and the **namespace requirement for `KubeadmControlPlane` clusters**.
- **Workload kubeconfig hardening** (#190). The provider now treats every
  workload kubeconfig as untrusted input. See [Security](#security).
- **Every fix from v0.1.5**: the three k0s HA day-2 fixes (VIP certificate
  SANs, control-plane-minted join tokens, and the etcd leave when the member
  holds the VIP). See the [v0.1.5 release notes](v0.1.5.md).

## Security

- **Workload kubeconfigs are sanitized and pinned** (#190).
  - Only the control plane writes `<cluster>-kubeconfig`. Nodes PATCH a
    controller-created staging Secret, `<cluster>-kubeconfig-push`; the
    `KairosControlPlane` validates it and rebuilds the published kubeconfig.
  - Every kubeconfig the controllers use accepts only inline credentials and
    an inline CA. The server is set from the Cluster's control-plane endpoint,
    and the CA is pinned the first time one is accepted.
  - This covers the published kubeconfig, the control plane's own workload
    clients, and the kubeadm worker path.
  - A published kubeconfig that fails validation is emptied in place, and
    `KubeconfigReady` reports `WaitingForNodePush` until it is republished.
- **Narrower node permissions** (#190). The node push token can only `patch`
  two named, controller-created Secrets: the kubeconfig staging Secret and the
  etcd-status Secret. Roles created by earlier versions are narrowed at
  startup.
- **Node-to-management calls verify TLS** (#190). Every call uses
  `curl --cacert` against the management API CA, with no insecure fallback,
  and the push token is no longer passed on the command line.
- **Go dependencies**: `golang.org/x/crypto` v0.58.0 (#174), plus the routine
  updates since v0.1.4.

**After upgrading:**
- Existing `<cluster>-kubeconfig` Secrets are revalidated, and rebuilt or
  emptied, on the first control-plane reconcile after the upgrade. Until then,
  other consumers read the stored copy, so upgrade promptly. As a general
  precaution, operators may review their management cluster's audit logs.
- The kubeconfig CA is pinned on first use, in the `kubeconfig-ca-pin`
  annotation on each `KairosControlPlane`. On upgrade, that is the CA of the
  current kubeconfig. Check it, and re-pin explicitly if it is not what you
  expect.
- As in the standard Cluster API model, principals that can write Secrets in a
  cluster's namespace on the management cluster remain trusted.

## Fixed

- **kubeadm worker token lifetime** (#191). A worker that ran `kubeadm join`
  more than 15 minutes after its first bootstrap render failed: the token was
  never extended, and the regeneration that adds the providerID replaced it.
  One token per worker is now reused across every render, extended until the
  node joins, and revoked once it has.
- **kubeadm patches directory** (#148). `kubeadm join` failed when the
  providerID patch was passed with `--patches` next to `--config`. The patches
  directory is now named in the `JoinConfiguration`, created before the
  node's one join attempt, and restricted at admission to a path under
  `/etc/kubernetes/`.
- **The KCP's own template reference** follows the same-namespace rule as
  other references (#126).
- Everything listed in the [v0.1.5 release notes](v0.1.5.md).

## Known issue

- **A k0s control-plane Machine that joined etcd but never got a Node
  reference is removed without leaving etcd.** See the
  [v0.1.5 release notes](v0.1.5.md#known-issue) for the workaround. A fix is
  designed for a later release.

## Upgrade notes

```bash
kubectl apply -f https://github.com/kairos-io/cluster-api-provider-kairos/releases/download/v0.2.0/kairos-capi-provider.yaml
```

Or, with `clusterctl`, upgrade both providers to v0.2.0. `metadata.yaml` now
lists the 0.2 series, with the same v1beta2 contract.

### Behaviour changes to expect

- **Node pushes need a management CA.** By default, nodes verify the
  management API against the controller's in-cluster CA. If the management
  API is reached through a load balancer or proxy that CA does not cover, set
  `KAIROS_MANAGEMENT_API_CA_FILE` on the bootstrap provider (an inline PEM or
  a path). Without a usable CA, a control-plane `KairosConfig` reports
  `BootstrapReady=False(ManagementCAUnavailable)` and no userdata is
  rendered. See
  [Node-to-management pushes are now TLS-verified](../UPGRADING.md#node-to-management-pushes-are-now-tls-verified).
- **Nodes booted before the upgrade** keep their old bootstrap data. Their
  next push is refused (a one-time 403) because their Role was narrowed; they
  pick up the new behaviour when they are replaced. See
  [Node-push RBAC narrows to patch-only](../UPGRADING.md#node-push-rbac-narrows-to-patch-only-and-the-push-target-moves-to-a-staging-secret).
- **Control-plane workload operations wait for the CA pin**, including the
  k0s etcd leave and join-token issuance. The first reconcile after the
  upgrade may requeue once.
- **kubeadm workers:** a control plane whose kubeconfig uses file paths, exec
  or auth-provider plugins, or several contexts is refused.
  `KubeadmControlPlane` and Kamaji publish self-contained kubeconfigs and are
  unaffected.

## Versions

- Cluster API v1.13.4 (v1beta2 contract), management and workload Kubernetes
  v1.30 to v1.36, and Kairos v4.1.2, as in v0.1.x. See the
  [v0.1.0 release notes](v0.1.0.md#compatibility).
- kubeadm workers are tested with kubeadm v1.30 (v1beta3) and v1.36
  (v1beta4).
- The image is built with Go 1.26.9.
