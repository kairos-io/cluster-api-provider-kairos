# v0.1.5 — Release Notes

A fix release for the v0.1 series, for **k0s control planes with high
availability** (`replicas` > 1 with a kube-vip VIP). It fixes three day-2
failures found while re-verifying v0.1.4 live: replacing control-plane members
could leave the cluster unable to add new members, or stuck removing an old
one. Every fix was validated live on vSphere with 3× k0s and a kube-vip VIP.

There is no CRD schema change. Single-node control planes, k3s, and worker
nodes are not affected by these bugs.

## Highlights

- **New k0s control-plane members serve a certificate valid for the VIP**
  (#163). Only the first control-plane node carried the control-plane
  endpoint in its API server certificate. When the VIP moved to any other
  member, clients that verify TLS against the endpoint failed.
- **The control plane now mints each joining k0s member's token itself**
  (#166). The controller-join token used to be created once, on the first
  node, pointing at that node's address, with a 24-hour expiry.
  - Once the first node was replaced (for example by a `spec.version`
    rollout), no new member could join.
  - On a cluster older than a day, no member could join at all.

  The `KairosControlPlane` now issues one short-lived token per joining
  member, through the workload API, pointed at a member that is alive.
- **Removing the member that holds the VIP no longer stalls** (#181, #182,
  #183). The etcd-leave handshake went through the control-plane endpoint.
  When the member being removed held the VIP, the endpoint was its own API
  server, which loses its etcd backend during the leave. The Machine stayed
  in `Deleting` indefinitely.

## Fixed

- **API certificate SANs** (#163). Every k0s control-plane member now lists
  the control-plane endpoint in its API SANs, not just the first.
- **Controller-join tokens** (#166).
  - Each token is a `bootstrap.kubernetes.io/token` Secret in the workload
    cluster's `kube-system`, valid for 1 hour.
  - It is extended in place while its member is still joining, up to 24 hours
    after the Machine was created, and deleted once the member has joined.
  - It points at a live member's k0s API (`:9443`), chosen from the
    `default/kubernetes` endpoints and this control plane's own Machines.
  - The first node no longer creates or pushes a token.
- **etcd leave on the control-plane side** (#181).
  - The `KairosControlPlane` sends the leave request and reads the
    acknowledgement through a member that is staying, not through the
    endpoint. The endpoint is a last resort.
  - Every request to the workload cluster is bounded (5s per member, 10s
    through the endpoint).
  - The leave starts only once Cluster API has finished draining the node and
    detaching its volumes, as the kubeadm control plane does.
  - If the node has not acknowledged within 5 minutes, the control plane asks
    k0s to remove the member (`spec.leave` on k0s's `EtcdMember`). It releases
    the Machine only once k0s reports the member gone. Before, it released the
    Machine with a warning that the member might be orphaned.
- **VIP ownership** (#182). kube-vip now elects its leader through its own
  node's API server (`127.0.0.1:6443`) rather than through the cluster
  Service. A member whose API server has lost etcd now gives up the VIP within
  seconds, instead of holding it while a healthy peer answered for it.
- **The node's etcd-leave responder** (#183).
  - Every call is bounded, and the acknowledgement is retried.
  - A completed leave is never run twice.
  - A `k0s etcd leave` that failed is no longer acknowledged as done.

## Security

- **`golang.org/x/crypto` v0.57.0 to v0.58.0** (#186), with `x/sync`,
  `x/sys`, `x/term`, `x/text` and `x/tools`. This is routine maintenance:
  `govulncheck` reports no vulnerability reachable from the provider at
  v0.57.0. The only advisory listed for the module, GO-2026-5932 (the
  unmaintained `openpgp` package), has no fix and is not used.
- **The node-push Role narrows** (#166). Nodes no longer get access to the
  control-plane join-token Secret. Existing Roles narrow on the cluster's next
  control-plane render.

## Changed

- **New annotations**, written by the `KairosControlPlane`:
  - on a joining member's `KairosConfig`:
    `controlplane.cluster.x-k8s.io/k0s-join-token-id` and
    `controlplane.cluster.x-k8s.io/k0s-join-token-removed-at`;
  - on a control-plane Machine being removed:
    `controlplane.cluster.x-k8s.io/etcd-member-leave-requested-at` and
    `controlplane.cluster.x-k8s.io/etcd-member-leave-member-id`.
- **New events** on the `KairosControlPlane`: `K0sJoinTokenMinted`,
  `K0sJoinTokenNoLiveMember`, `K0sJoinTokenMissing`,
  `K0sJoinTokenServerUnavailable` and `EtcdMemberLeaveDelegated`.

## Known issue

- **A control-plane Machine that joined etcd but never got a Node reference
  is removed without leaving etcd.** This can happen when a new member's
  `providerID` is never set, for example after a very slow provisioning.
  Deleting that Machine leaves its etcd member behind, and a later member
  created with the same name can fail to join correctly.
  - **Before deleting a control-plane Machine that has no `status.nodeRef`,**
    check `k0s etcd member-list` on a healthy member. If the Machine's member
    is listed, remove it first, with `k0s etcd leave --peer-address <ip>` on a
    healthy member, or by setting `spec.leave: true` on its `EtcdMember`.
  - A fix is being designed for a later release.

## Upgrade notes

```bash
kubectl apply -f https://github.com/kairos-io/cluster-api-provider-kairos/releases/download/v0.1.5/kairos-capi-provider.yaml
```

Or, with `clusterctl`, upgrade both providers to v0.1.5.

- **Nodes keep the bootstrap data they were created with.** The kube-vip
  change (#182) and the responder change (#183) reach only control-plane
  members created after the upgrade, for example by a rollout. The
  control-plane changes (#166, #181) apply at once.
- **A Machine already stuck in `Deleting`** at the etcd-leave hook recovers
  after the upgrade: the control plane hands the leave to k0s and releases
  the Machine once k0s reports the member gone. On members created before
  v0.1.5, Cluster API's own drain can still wait on the old VIP holder. If the
  Machine stays at `DrainingNode`:
  1. Set `KairosControlPlane.spec.machineTemplate.nodeDrainTimeout`, for
     example `2m`. It also applies to Machines already draining.
  2. If it then waits at volume detach, set
     `spec.deletion.nodeVolumeDetachTimeoutSeconds` (for example `60`) on
     that Machine.
- **A joining member stuck on an old token** (Machine `Provisioned`, no Node)
  does not recover on its own: delete that Machine, and a new one gets a
  token from the control plane.
- **kube-vip reaches the API server on loopback.** Members created after the
  upgrade need the API server listening on `127.0.0.1:6443`, which is the k0s
  and k3s default. A custom API server port, or a bind address that excludes
  loopback, leaves the VIP down.
- **The first rollout after the upgrade** can restart kube-vip a few times
  while old and new members disagree on its spec. Each restart is a VIP
  failover of a few seconds.
- First control-plane nodes created by v0.1.4 or earlier keep a leftover
  `/tmp/kairos-jointoken-push.log`. It is no longer used and can be deleted.

## Versions

- Unchanged from v0.1.4: Cluster API v1.13.4 (v1beta2 contract), management
  and workload Kubernetes v1.30 to v1.36, and Kairos v4.1.2. See the full
  table in the [v0.1.0 release notes](v0.1.0.md#compatibility).
- The image is built with Go 1.26.9, as in v0.1.4.
- kubeadm workers are not in this release. They arrive in v0.2.0.
